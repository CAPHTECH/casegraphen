# Issue #89 implementation local-optima audit

## Scope and evidence

This `intervention` audit covers `runtime-durability-evidence.py`, the
protected publication workflow, its bounded fixtures and conformance gate, the
Issue #85 legacy baseline pointer, and the first retained Release record under
`docs/pilots/issue-89`.

Observed execution evidence includes failed workflow runs `30956780276`,
`30957090184`, `30957510318`, and `30957773488`, successful protected run
[`30958980480`](https://github.com/CAPHTECH/casegraphen/actions/runs/30958980480),
the content-addressed Release asset with SHA-256 `703c783b...`, a second
download outside the workflow, and strict offline verification returning
`verified: true`. The failed `8767d1f5...` Release remains available with
explicit **NON-RETAINED** notes and no `retained_release` record.

Unobserved evidence is limited to administrator deletion/replacement behavior,
long-term retention, production-scale package growth, and WORM or transparency
log mirroring. GitHub Releases are not claimed to provide those properties.

## System outcome and evaluation frame

The system outcome is durable, independently re-checkable runtime evidence
without making every source clone retain all generated bytes or converting
retention into acceptance authority.

| Item | Evaluation condition |
| --- | --- |
| `B` | package builder → protected publisher → GitHub Release → checked-in exact record → offline verifier |
| `M` | deterministic bytes, exact SHA/length, no-clobber publication, reproducibility, bounded repository growth, `accepted: false` |
| `N` | workflow, package contract, tests, documentation, environment policy, and Release metadata may change together |
| `T` | PR validation, failed publication, retry/new content address, later audit, and product-lifetime retention |
| Constraints | exact trusted commit, required reviewer, no API keys, GitHub Release mutability, ordinary CI without historical downloads |

## Detailed cards and compensation halo

### Checked-in generated evidence

- **Local rationality:** all evidence is available in a source checkout with no
  external service.
- **Beneficiary:** one reviewer inspecting one pilot.
- **Compensation halo:** every developer, CI cache, mirror, backup, and later
  clone pays for all historical generated bytes.
- **Inversion:** repository/lifecycle boundary. The selected design retains one
  capped baseline and future small records while moving bulk bytes to a
  content-addressed Release.

### Combined build-and-measure command

- **Local rationality:** `cargo run` ensures the executable exists and then
  invokes it in one step.
- **Observed failure:** run `30957090184` passed the allocator release pilot but
  reported aggregate threshold failure because `/usr/bin/time` included the
  compiler child RSS in a runtime-child memory metric.
- **Burden:** release operators receive a false durability failure and must
  diagnose hosted-runner-only behavior.
- **Resolution:** `cargo build` is completed first; `/usr/bin/time` wraps only
  `target/debug/examples/runtime_reconciliation_durability_pilot`. Failure-only
  diagnostic artifacts prevent future blind threshold failures.

### Divergent manifest ordering

- **Local rationality:** sorting the internal package inventory makes package
  construction deterministic while retaining the source manifest as emitted.
- **Observed failure:** run `30957773488` uploaded exact bytes, then strict
  offline verification rejected `source/package inventory mismatch`.
- **Burden:** the publisher created a non-retained Release and operators had to
  distinguish uploaded bytes from accepted retention evidence.
- **Resolution:** the builder now writes the same path-sorted inventory to the
  canonical source and internal manifests. A reversed-input regression proves
  producer ordering cannot recreate the defect. The failed asset was not
  deleted or blessed; its notes and absence of a retained record preserve the
  failure boundary.

## Widened-boundary comparison

| Boundary | Narrow/local choice | Selected cross-boundary design | Advantage |
| --- | --- | --- | --- |
| One run | Commit reports or upload once | Deterministic package plus small record | Narrow choice is simpler |
| Workflow | Infer cwd and combine build/run | Explicit repository and separately measured executable | Selected design after real failures |
| Repository | Monotonic bulk history | One capped baseline plus small exact pointers | Selected design |
| Independent re-audit | Trust upload response or URL | Fresh download, SHA/length, safe extract, inventory and deterministic rebuild | Selected design |
| Administrative lifetime | Call hash-named Release immutable | State explicitly that Release is mutable; retain optional WORM mirror | Selected design is honest but not WORM |

## Counterfactuals and migration valley

- **A — legacy/current-state fallback:** continue checking in every generated
  report. Rollback is easy but repository cost grows monotonically.
- **B — narrow upload:** use an Actions artifact or Release pointer without
  canonical packaging, conflict inspection, or offline rebuild. Publication
  is cheaper, but later auditors inherit unverifiable claims.
- **C — selected cross-boundary design:** exact trusted commit, required-review
  publisher environment, canonical archive, hash-derived Release identity,
  create-new/no-clobber inspection, re-download, strict offline verification,
  and checked-in exact small record.

The migration valley was observed rather than hidden. The first debug allocator
run exceeded its release threshold, compiler RSS polluted the runtime metric,
implicit `gh` context failed, and an ordering defect produced a non-retained
asset. Each failure stayed fail-closed. No Release was deleted or overwritten;
the successful corrected input produced a different package hash/tag. Rollback
still means disabling publication and relying on the capped legacy baseline,
not deleting evidence or changing ledger authority.

## False positives and non-candidates

- Keeping one bounded baseline anchors the migration and is conformance-capped;
  it is not recurring bulk retention.
- Sharing the fresh-agent deterministic archive and Release inspection helper
  is deliberate decision-rule reuse, not accidental coupling.
- The required-reviewer environment did provide a real manual deployment seam.
  Its same-account approval is only a promotion-evidence limitation, not a
  claim that the publication mechanism failed.
- The failed Release is not contradictory retained evidence: it has explicit
  NON-RETAINED notes and no retained record.

## Verdict and residual evidence

Within the investigated builder→Release→offline-verifier boundary, the chosen
design is preferable to checked-in bulk or pointer-only publication. Three
implementation-local assumptions inverted under the real hosted workflow and
were corrected with C3 execution evidence. Overall verdict: `mixed` during the
migration, now bounded by fail-closed contracts.

Next evidence should observe retention and package-size trends over multiple
runs, administrative deletion/recovery behavior, and—only if stable promotion
requires it—an independently controlled publication reviewer or WORM/
transparency mirror. None of those gaps authorizes treating this retained
package as accepted CaseGraphen evidence.
