# Issue #89 implementation local-optima audit

## Scope and evidence

This audit covers the runtime-durability retention boundary introduced for
Issue #89: `runtime-durability-evidence.py`, its GitHub workflow, the bounded
fixture/tests, the last-baseline marker under `docs/pilots/issue-85`, and the
conformance gate. It does not claim that an external Release has already been
published or that GitHub Releases provide WORM retention.

Observed evidence: deterministic-package tests, offline tamper rejection,
exact retained-file inventory, explicit package/member budgets, and reuse of
the fresh-agent publication verifier. Unobserved evidence: an actual protected
workflow publication, administrator deletion behavior, and production-scale
package growth.

## Evaluation frame

- **B — boundary:** package builder → protected publisher → GitHub Release →
  checked-in small retention record → independent offline verifier.
- **M — metrics:** deterministic bytes; exact SHA/length; create-new,
  idempotent, no-clobber publication; offline reproducibility; repository and
  CI byte budgets; no authority escalation.
- **N — needs:** preserve audit evidence without perpetual Git growth, retain
  exact workflow/commit/topology/deployment identity, and keep routine CI
  independent of historical downloads.
- **T — time:** pull-request checks, one publication attempt, retry/concurrent
  publication, later offline audit, and long-lived repository history.

## Candidate detail and compensation halo

The old checked-in report set was locally rational: reviewers could inspect
all bytes without another service. Its compensation halo was distributed to
every future clone, cache, checkout, inventory walk, and backup. Freezing it as
the explicit last baseline preserves historical reproducibility while moving
future growth outside Git.

A bespoke runtime archive would also be locally rational, but would duplicate
the most security-sensitive decision rules from fresh-agent evidence. The
implementation instead delegates canonical tar/gzip construction and Release
inspection/SHA verification to the established helper. Runtime-specific code
owns only its typed evidence contract.

## Widened-boundary comparison

| Boundary | Checked-in bulk | Selected design |
| --- | --- | --- |
| One run | Simplest | Slight publication overhead |
| Repository | Monotonic large-file growth | One frozen baseline plus small records |
| CI fleet | Repeated local/network cost | Small generated fixture only |
| Independent auditor | Bytes present but mixed with source history | Exact content address plus offline self-verification |
| Administrative lifetime | Git retention strong but expensive | Release is mutable; explicitly not WORM |

## Counterfactuals

- **A — current/legacy:** append each report directory to Git.
- **B — narrow local fix:** upload an artifact or Release without canonical
  packaging, conflict checks, or offline rebuild.
- **C — cross-boundary design (chosen):** canonical package, hash-derived
  tag/asset, protected exact-SHA publisher, create-new/no-clobber inspection,
  re-download verification, and a small retention record.

## Migration valley and rollback

The migration intentionally retains the Issue #85 bytes as the final legacy
baseline. Until the first protected Release is published, the new record stays
`publication_pending` and cannot be presented as retained evidence. A failed
or ambiguous publication is retried against the same content address; a
conflicting asset fails closed. Rollback means disabling the publication
workflow while retaining the baseline and scripts; it never deletes evidence
or changes ledger authority.

## False positives / non-candidates

- Keeping one bounded baseline is not itself a local optimum; it anchors the
  migration and is conformance-capped.
- GitHub Release mutability is not hidden: the docs explicitly deny WORM
  semantics.
- Reusing the fresh-agent helper is not accidental coupling; deterministic
  packaging and no-clobber inspection are intentionally shared decisions.

## Residual evidence needed

Run the protected workflow, retain the resulting record in a reviewed commit,
re-download and verify it from an independent environment, then observe
package size/member trends. Those are promotion evidence, not prerequisites
for testing the repository mechanism.
