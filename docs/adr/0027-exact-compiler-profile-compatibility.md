# ADR 0027: Reviewed bundles retain exact compiler profile compatibility

- Status: Accepted for experimental v0
- Date: 2026-08-05

## Context

Semantic deployment-bundle verification recompiles `compiler.inputs.json` and
requires every generated byte to match. That proves compiler provenance, but a
single moving implementation identity would either strand historical reviewed
bundles or tempt a future verifier to reinterpret old inputs with new lowering
semantics. Full recompile cost also needs an observable fleet budget before the
contract can be promoted.

## Decision

Every new bundle binds an implementation name, exact compiler profile version,
semantic-profile identifier, and the complete set of compiler-input contract
versions. Profile 1 uses `graph_compiler.inputs.v1`; profile 0 and its v0 input
shape remain an exact, separately dispatched compatibility implementation.
Unknown, substituted, or future identity/schema pairs fail closed. No default
fields or best-effort parsing may reinterpret a historical input record.

Topology review binds the exact compiler version, semantic profile, retained
input schema, and contract-inventory hash. Canonical reviews written before
that binding replay as profile 0 only; they cannot authorize a profile 1
compile or resource authority. Selecting a new compiler profile therefore
requires a fresh content-bound topology/policy review. A migration proposal is
evidence for that review, never a substitute for it.

Canonical verification still performs one full deterministic recompile and
byte-compares the manifest and every artifact. It may return non-authoritative
cost observations, but those observations and any replaceable cache cannot
create deployment authority.

A historical-profile upgrade produces only a content-addressed migration
proposal. The proposal binds source and proposed bundle hashes and complete
source/target compiler migration identities: version label, implementation,
profile version, semantic-profile contract, compiler-input schema, and the
content hash of the compiler contract-version inventory. Version-only fields
are forbidden. It also binds topology and policy hashes and changed artifact paths. It contains
no proposed bundle bytes, is always `accepted: false`, and requires a separate
review before any future materialization or supersession workflow.

## Consequences

- Historical authority remains auditable with its exact compiler profile.
- Compiler semantic changes require a new profile and retained verifier rather
  than silently changing `GRAPH_COMPILER_VERSION` behavior.
- Supporting a historical profile has an explicit maintenance cost; removal
  requires a separately reviewed retention and migration decision.
- Verification latency and memory remain promotion evidence, never authority.

## Promotion evidence

Retain same-profile, historical-profile, identity substitution, contract
substitution, future-version, and migration-proposal tests. Release pilots must
measure small, medium, and large topology verification latency, process peak
memory, input bytes, artifact count, and recompile count. Stable promotion is
refused if semantic equivalence fails or the documented performance budget is
exceeded.

Profile 0 is locked by multiple content addresses covering the base proposal,
an alternate topology/request, and a reviewed-mode bundle. These hashes address
the complete manifest and artifact inventory; changing shared lowering requires
a new profile rather than updating historical expectations.
